A production-grade LLM and Retrieval-Augmented Generation (RAG) system requires tracking two complementary tiers of observability [1, 2]: **operational metrics** (telemetry covering latency distributions, hardware utilization, token spend, and errors) [1, 3, 4] and **quality metrics** (measuring candidate retrieval precision, reranking quality, and generative grounding) [5-7]. 

The metrics, alert thresholds, and dashboard architecture recommended across the OpenTelemetry GenAI standards, Dynatrace AI observability reference, and related sources outline specific implementation patterns [1, 8, 9].

---

### **1. Operational & System Telemetry Metrics**

#### **A. Latency & Phase Decomposition**
Measuring overall request duration alone obscures whether delays stem from gateway queues, slow cross-encoders, prefill bottlenecks, or autoregressive generation [3, 10, 11]. Observability sources decompose latency across client and server viewpoints [10-13]:
* **Time-to-First-Token (TTFT) / Time-to-First-Chunk**:
  * **Client-side** (`gen_ai.client.operation.time_to_first_chunk` or `gen_ai.client.inference.time_to_first_chunk`): Measures the delay from the initial client request to the moment the first streamed response chunk arrives [10, 12, 14].
  * **Server-side** (`gen_ai.server.time_to_first_token`): Tracks queuing delay and prompt prefill computation within the inference engine (vLLM, SGLang, NIM) [10, 13, 15]. Focus on **median (p50)** and **p95** to assess interactive responsiveness [16, 17].
* **Time-Per-Output-Token (TPOT) / Time-Between-Tokens (TBT)**:
  * Emitted as `gen_ai.client.operation.time_per_output_chunk` or `gen_ai.server.time_per_output_token` [10, 12, 13]. Tracks generation velocity during the decode phase [10, 18].
* **Operation & Workflow Durations**:
  * `gen_ai.client.operation.duration`: End-to-end call duration (tracked at **p50, p90, and p95/p99**) [12, 19-21].
  * `gen_ai.execute_tool.duration`: Latency per tool invocation [22, 23].
  * `gen_ai.invoke_agent.duration`: Duration of a full in-process agent execution from start to final response [22, 24].

#### **B. Token Consumption & Financial Spend**
OpenTelemetry does **not** provide a direct monetary cost metric or attribute; token counts act as the proxy and are multiplied downstream against model pricing schedules [4, 25, 26].
* **Token Histograms & Counters**: Monitored via `gen_ai.client.token.usage` split by `gen_ai.token.type` (`input` vs. `output`) [12, 27, 28].
* **Prompt Caching Audits**: `gen_ai.usage.cache_read.input_tokens` and `gen_ai.usage.cache_creation.input_tokens` track cache hits and writes to quantify static context reuse savings [28, 29].
* **Reasoning Overhead**: `gen_ai.client.inference.usage.reasoning.output_tokens` isolates internal chain-of-thought tokens from final visible output [28, 30].
* **Session Grouping**: Grouped using `gen_ai.conversation.id` to track total token burn across multi-turn chat threads [20, 31, 32].

#### **C. Error Taxonomy & Reliability**
* **Error Classification**: Standardized under `error.type` on spans and metric histograms [19, 31, 33]. Tracks provider exceptions, HTTP 5xx codes, `rate_limit`, `timeout`, and Pydantic/Zod `ValidationError` [19, 31, 33, 34].
* **Cardinality Rule**: `error.type` must be restricted to low-cardinality error categories to prevent metric dimension explosion [35, 36].
* **Agent Recursion Spikes**: `gen_ai.invoke_agent.inference_calls` and `gen_ai.invoke_agent.tool_calls` count model calls and tool executions per invocation [30, 37]. A rising tail signals that an agent has entered an un-converged retry loop [38].

### **2. Retrieval & Generation Quality Metrics (RAG & Judges)**

#### **A. First-Stage Retrieval & Reranking Metrics**
* **Recall@K & Hit@K**: Measures whether the gold evidence chunks are present anywhere in the top-\\(K\\) candidate pool [7, 39]. Sets the absolute retrieval ceiling for the pipeline.
* **MRR (Mean Reciprocal Rank)**: Measures how early the *first* relevant chunk appears in the returned ranking [39, 40]. Highly correlated with Precision@5 (\\(r = 0.88\\)) [40].
* **nDCG@10 (Normalized Discounted Cumulative Gain)**: Primary ranking metric for second-stage rerankers (e.g., BGE-Reranker, Cohere) [5, 39, 40]. Uses a logarithmic discount (\\(\log_2(i+1)\\)) to evaluate graded relevance ordering [5].
* **Citation Rank Shift**: Tracks the rank of chunks actually cited by the generator before vs. after reranking [41]. If citations shift from rank 20–60 to rank 1–3, the reranker is delivering measurable value [41].

#### **B. Generative Grounding & Claim Metrics**
* **Faithfulness / Groundedness**: Ratio of atomic statements in the generated response that are logically supported by the retrieved context chunks (\\(\frac{|\text{Supported Claims}|}{|\text{Total Claims}|}\\)) [6, 7]. Isolates model hallucinations from retriever omissions [6, 7].
* **Context Relevance & Precision**: Evaluates the signal-to-noise ratio in retrieved context, identifying irrelevant distractor chunks [7].
* **Answer Relevancy**: Verifies that the output answers the user's initial query without wandering off-topic [7].

#### **C. LLM-as-a-Judge Scoring (G-Eval & Prometheus 2)**
* **G-Eval Probability-Weighted Score**: Generates step-by-step criteria instructions via Auto-Chain-of-Thought (Auto-CoT) and calculates the continuous expected score from token log-probabilities (\\(\text{Score} = \sum p(s_i) \cdot s_i\\)), eliminating integer tie artifacts and score compression [42-44].
* **Rubric Direct Assessment**: Uses fine-tuned open evaluators like Prometheus 2 with explicit 1–5 behavioral rubrics and reference anchors [45-47].
* **Online Eval Telemetry**: Live production traces are sampled asynchronously (10–20%), judged, and recorded as `gen_ai.evaluation.result` events or custom span attributes [48-51].

### **3. Production Alert Thresholds & Service Level Objectives (SLOs)**

| Metric Category | Target Metric | Recommended Alert Threshold / SLO | Operational Risk / Trigger Condition |
| :--- | :--- | :--- | :--- |
| **Prefill Responsiveness** | TTFT (`time_to_first_token` / chunk) [12, 13] | **p95 < 1.5s – 2.0s** (Interactive chatbots) [16, 17] | High queue times, long prompt contexts, or lack of prefix caching [52]. |
| **Decode Fluidity** | TPOT / TBT (`time_per_output_token`) [11, 13] | **p99 TBT < 5× decode baseline** [16] | Degraded decode throughput, token batch saturation, or scheduling delays [11, 16]. |
| **Error Budget** | `error.type` / Failed Requests [19, 33] | **Error rate > 1.0%** over a 5m baseline [49] | Provider rate limits (429), timeouts, or downstream service outages [31, 49]. |
| **Schema Integrity** | Pydantic / Zod `ValidationError` [34] | **Schema failure rate > 5.0%** [34] | Model drift after an upgrade or truncation due to max token limits [34]. |
| **Agent Loops** | `gen_ai.invoke_agent.inference_calls` [30, 37] | **> 10–12 calls per invocation** [38] | Runaway retry loops multiplying token spend exponentially [38, 53]. |
| **Serving Saturation** | `num_requests_waiting` (vLLM / NIM) [54, 55] | **Queue depth > 20 requests** [56] | GPU capacity exhausted; triggers auto-scaling pods [55, 56]. |
| **KV-Cache Memory** | `gpu_cache_usage_perc` [54, 55] | **KV-Cache utilization > 90%** [56] | Imminent VRAM Out-of-Memory (OOM) or request preemption [55, 56]. |
| **Faithfulness Score** | Claim verification score [6, 7] | **Rolling 24h average < 0.85** [49] | Prompt degradation, hallucination spike, or poor retrieval quality [7, 49]. |
| **Context Relevancy** | Chunk noise score [7] | **Rolling 24h average < 0.80** [49] | Inverted index / vector search drift returning irrelevant context [7, 49]. |

### **4. Recommended Production Dashboard Architecture**

Structuring panels logically across four distinct operational tiers isolates bottlenecks quickly [1, 57, 58]:

```
┌────────────────────────────────────────────────────────────────────────────────────────┐

│ [ Total Requests / QPS ]  [ Success Rate (1 - error.type) ]  [ 24h Spend ($) ]  [ p95 TTFT ] │
├────────────────────────────────────────────────────────────────────────────────────────┤
│ 2. LATENCY & SERVING DYNAMICS (vLLM / Model Server & Client View)                     │
│ ┌────────────────────────────────────────┐  ┌────────────────────────────────────────┐ │
│ │ Latency Histograms (TTFT vs TPOT)      │  │ Engine Saturation & Queue Depth        │ │
│ │ • Client p50/p90/p95 TTFT (Prefill)    │  │ • vllm:num_requests_running (Decode)   │ │
│ │ • Server Time Per Output Token (TPOT)  │  │ • vllm:num_requests_waiting (>20 alert)│ │
│ │ • E2E Duration by Model & Provider     │  │ • vllm:gpu_cache_usage_perc (>90%)     │ │
│ └────────────────────────────────────────┘  └────────────────────────────────────────┘ │

│ 3. TOKEN USAGE, PROMPT CACHE & AGENT DRIFT                                            │
│ ┌────────────────────────────────────────┐  ┌────────────────────────────────────────┐ │
│ │ Token Consumption Breakdown            │  │ Agent & Tool Execution Complexity      │ │
│ │ • gen_ai.client.token.usage (Input)    │  │ • invoke_agent.inference_calls per turn│ │
│ │ • gen_ai.client.token.usage (Output)   │  │ • execute_tool.duration by tool.name   │ │

└────────────────────────────────────────────────────────────────────────────────────────┘
```

#### **Panel Details**:
1. **Tier 1: High-Level Health & Financials**
   * **KPI Tiles**: Total requests, overall success rate, aggregate token spend (calculated from provider rate tables), and p95 TTFT [12, 20, 26].
   * **Filters**: Dynamic dropdowns for `gen_ai.provider.name`, `gen_ai.request.model`, and `service.name` [20, 57].
2. **Tier 2: Latency & Serving Dynamics**
   * Compares client-side perceived delay (`time_to_first_chunk`) with server-side queueing and prefill time (`time_to_first_token`) [10, 59].
   * Tracks GPU utilization (`gpu_cache_usage_perc`) and queue backlog (`num_requests_waiting`) to guide auto-scaling [54-56].
3. **Tier 3: Tokens, Caching, & Agent Control**
   * Visualizes token consumption by input, output, cache-read, and reasoning subsets [28, 60].
   * Monitors agent recursion via `invoke_agent.inference_calls` to catch infinite tool loops [37, 38].
   * Groups errors by `error.type` (`ValidationError`, `timeout`, `rate_limit`) to isolate integration failures [19, 31, 34].
4. **Tier 4: RAG Retrieval & LLM Judge Evaluation**
   * Displays first-stage candidate recall alongside second-stage nDCG@10 [5, 7].
   * Plots continuous rolling scores for Faithfulness and Context Relevancy generated via online sampling (G-Eval / Prometheus 2) [44, 48, 61].
   * Flags runs falling below the 0.85 faithfulness threshold and routes them directly to human review queues [49, 61].
