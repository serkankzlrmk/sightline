Based on the sources in this notebook, your current production pipeline—**fixed 800-character chunks (~150–200 tokens) with 150-character overlap, 384-dimensional `all-MiniLM-L6-v2` dense embeddings, no cross-encoder reranker, and naive RRF with \\(k=60\\) over 3 sub-queries in ChromaDB**—suffers from three structural bottlenecks:

1. **Arbitrary segmentation & boundary loss**: Fixed character splitting treats text uniformly, routinely severing sentences, table rows, and logical thoughts mid-argument [1-4].
2. **First-stage ordering failure ("Lost in the Middle")**: While vector recall may pull relevant candidates somewhere in the top 50, the absence of a cross-encoder means the generator often sees suboptimal passages at ranks 1–5 [5-8].
3. **Lexical exact-match blindness**: Relying purely on dense vector sub-queries causes severe degradation on exact technical entities, product codes, UUIDs, and acronyms [9-12].

### **Priority 1: Introduce a Second-Stage Cross-Encoder Reranker**
*The highest quality lift per dollar and compute cycle in any RAG stack [7, 13].*

* **The Problem**: A vector retriever retrieves candidates, but cannot accurately evaluate fine-grained token-level cross-attention [6, 7, 14]. Without a reranker, the most relevant passage often lands at rank 15–30, where generative LLMs suffer from "Lost in the Middle" attention degradation [7, 8, 15].
* **Concrete Solution**: 
  * Take the top 50–100 candidates returned by the candidate store and pass them through a cross-encoder model to select the top 3–5 passages for the generation prompt [16-19].
* **Model Choices & Trade-offs**:
  * **Option A (Self-Hosted / Open Source — Recommended Default)**: **`bge-reranker-v2-m3`** (568M params, Apache 2.0) [17, 20, 21].
    * *Impact*: Lifts Hit@1 and Recall@5 by +11 to +18.4% over raw bi-encoder baselines [17, 19, 22].
    * *Latency / Cost*: ~80–140 ms per 100 candidates on GPU (T4/A10/M-series) [17, 19, 23]; costs zero API fees [17, 22]. *(Watch out: 512-token sequence limit [21, 23]).*
  * **Option B (Managed API / Zero Ops)**: **Cohere Rerank (v3.5 / Rerank 5)** [17, 24, 25].
    * *Impact*: Highest managed quality (82.2 RCP-nDCG@10 on BRIGHT) [19, 26].
    * *Latency / Cost*: ~200–600 ms (network roundtrip); billed at ~\$2.00 per 1,000 searches or \$0.05/M tokens [17, 27, 28].
  * **Option C (High-Capacity Open Weights)**: **Qwen3-Reranker-4B** [17, 24, 29].
    * *Impact*: Highest open-weight ranking quality (0.671 nDCG@10, +27.1% Recall@5 lift) [17].
    * *Latency / Cost*: Slower (~312–478 ms on GPU, 6.8 GB VRAM footprint) [17].
* **Budget Rule**: Never rerank an unbounded candidate pool (reranking 500+ candidates incurs a 485–2000× latency blowout) [30]. Restrict rerank depth to \\(N=50\text{--}100\\) [16, 19, 30].

### **Priority 2: Decouple Retrieval from Generation via Parent-Child (Hierarchical) Chunking**
*The most consequential architectural change to solve the precision-recall trade-off [31-34].*

* **The Problem**: 800-character fixed chunks (~150–200 tokens) create an irreconcilable conflict: they are either too large to give sharp semantic cosine scores or too small for the LLM to understand complete tables, qualifiers, and background context [1, 32, 35].
* **Concrete Solution**: Implement **Parent-Child Chunking (Small-to-Big)** [31, 32, 34, 36]:
  1. Segment text into **Child Chunks** (100–250 tokens / ~3 sentences with 1–2 sentence overlap) [34, 35, 37]. Embed only the child chunks into ChromaDB for search [31, 34, 36].
  2. Store corresponding **Parent Chunks** (500–1,500 tokens / full logical sections) in a key-value document store [32, 34, 35].
  3. *At Query Time*: Retrieve on child vectors, run candidate deduplication/reranking, but inject the enclosing **Parent Chunk** into the LLM context [31, 32, 34, 35].
* **Expected Impact**: Decoupling retrieval from generation eliminates context starvation and missing qualifiers, lifting generation faithfulness from ~0.70 to ~0.84+ [38, 39].
* **Alternative Approaches Evaluated in Sources**:
  * **Late Chunking (arXiv:2409.04701)**: Computes a single embedding pass across the entire document using a long-context embedder (Jina v3, Voyage 3, Cohere Embed), then mean-pools chunk vectors [40-43]. Preserves long-range cross-chunk anaphoric dependencies [42-44], but requires discarding `all-MiniLM-L6-v2` (512-token context limit) [44, 45].
  * **Pure Semantic Chunking (Similarity Threshold Drop)**: Groups sentences by embedding cosine similarity [46-48]. While semantically aware, it produces unpredictable chunk distributions (some 50 tokens, some 1,800 tokens), causing feature dilution and embedding noise [49-51], and requires 3–10× more embedding computations during ingestion [52, 53].
  * **Structure-Aware / Paragraph-Group Chunking (PGC)**: Grouping text along natural paragraph boundaries (e.g., 2 paragraphs with 1 paragraph overlap) achieves the highest mean nDCG@5 (0.459) across 36 evaluated strategies, beating naive fixed-character chunking (0.244 nDCG@5) by over 10× in rank-1 precision [3, 54, 55].

### **Priority 3: Convert Pure Dense Retrieval to True Hybrid (BM25 + Dense Vectors)**
*Eliminating exact-match keyword blindness [9-12].*

* **The Problem**: Dense embeddings (`all-MiniLM-L6-v2`) project text into continuous concept space. When users search for exact serial numbers, error codes, UUIDs, or domain acronyms (e.g., `"wal_level = logical"` or product IDs), dense vector search treats them as embedding noise and suffers severe recall failures [9, 10, 12, 56].
* **Concrete Solution**: 
  * Add an inverted index lexical search channel (**BM25**) alongside ChromaDB [11, 57, 58].
  * Execute BM25 and vector search in parallel [58, 59].
* **Expected Impact**: 
  * Fusing BM25 with dense retrieval increases Recall@100 across every BEIR dataset (e.g., MSMARCO jumps from 0.66 to 0.80, NQ from 0.75 to 0.92) [5, 60]. 
  * On exact product/code queries, BM25 captures up to 70% of relevant documents that dense search misses entirely [61, 62].
* **Latency Trade-off**: Adds only minimal CPU overhead when queried in parallel (BM25 typically resolves in <10–30 ms) [30, 58, 59, 63].

### **Priority 4: RRF Tuning and Sub-Query Calibration**
*Optimizing fusion rank stability and candidate depth [64-66].*

* **The Problem in Current Setup**: RRF with \\(k=60\\) over 3 dense sub-queries is simply averaging multiple views of the *same* dense retriever. RRF is designed to merge fundamentally different, scale-incompatible rank distributions (e.g., lexical BM25 vs. dense cosine) [64, 66-68].
* **Concrete Optimization**:
  1. **RRF Channel Re-architecture**: Fuse 1 BM25 ranked list with the dense vector ranked lists (or use query decomposition to generate 1 lexical + 2 dense sub-queries) [65, 69].
  2. **Candidate Retrieval Depth (Window Size)**: Pull **\\(N = 50\text{--}100\\) candidates per retriever** before running RRF [16, 59, 70, 71]. If fusion depth is too small (e.g., top 10), documents ranked at position 15 in BM25 and position 12 in dense will be clipped to 0, destroying consensus benefits [70, 72].
  3. **Tuning Constant \\(k\\)**:
     * Keep **\\(k = 60\\)** as the production default [59, 73-75]. It provides a smooth, scale-free curve where consensus across retrievers outweighs single-list outliers [64, 65, 74].
     * *When to adjust*: If feeding directly to a cross-encoder reranker, increasing \\(k\\) to **80–100** flattens rank decay and protects candidate recall in the tail [76]; if serving final results directly to users without a reranker, \\(k \in [77, 78]\\) sharpens top-rank precision [76].
  4. **Weighted Fusion vs. RRF**: If you establish a judged golden evaluation set and find dense retrieval is systematically stronger, a weighted linear combination (\\(\alpha \approx 0.7\\) dense, \\(0.3\\) BM25) can yield slightly higher nDCG@10 than raw RRF [60, 79-81]. However, unweighted RRF remains the most operationally stable default against score distribution drift [16, 82, 83].

### **Priority 5: Re-evaluate Embedding Model Sensitivity (`all-MiniLM-L6-v2`)**
*Address capacity ceilings without premature optimization [84-87].*

* **The Reality from Benchmark Studies**:
  * Empirical benchmarks evaluating 36 chunking strategies across 5 embedding models show that **`all-MiniLM-L6-v2` is the second-strongest baseline (mean nDCG@5 = 0.416)**, trailing only modern 1024-dim models like **`bge-m3` (0.456)** [84, 88].
  * *Critical Finding*: **Chunking and reranking dominate embedding model size** [13, 85, 86, 89]. High-capacity embeddings cannot overcome bad chunks (FCC character chunking remains crippled at nDCG < 0.244 regardless of embedding size) [3, 54, 85, 86].
* **Actionable Recommendation**:
  * **Do not swap embeddings first** [87, 90]. Keep `all-MiniLM-L6-v2` while you implement Parent-Child chunking, BM25 hybrid search, and the BGE reranker [13, 39, 87].
  * *Next Upgrade Step*: Once chunk boundaries and rerankers are stable, upgrade the dense embedding model to **`bge-large-en-v1.5`** or **`bge-m3`** (or a long-context embedder like Jina v3 / Voyage 3 if migrating to Late Chunking) to capture an additional 3–5 percentage points of nDCG [45, 84, 88, 91].
