## Problem Statement

Sightline's crawlable surface is live but its content is too thin for Google to rank: (1) weekly bulletin JSON with 1-line country summaries, (2) 49 country summaries with deterministic data-driven narratives (explicitly NO LLM), (3) `/crisis/<slug>` SSR pages rendering that data. Founder's diagnosis (Q2): "Content too thin — Google won't rank 1-line summaries, need richer daily/weekly pages with real analysis depth." Success driver (Q6): organic search — Google indexing richer pages, ranking for crisis+country long-tail, pulling anonymous readers who then see CTAs.

## Demand Evidence

- Sector-insider knowledge: crisis-time SITREP production is a documented all-nighter problem; M&E officers pay for pre-digested analysis.
- Competitive void (Aug 30 research, still holds): ACAPS-style analysis is the gold standard but human-analyst-bound; ReliefWeb is the raw firehose with weak presentation. The crisis×country×theme long-tail remains unclaimed.
- Honest gap (unchanged): no external user count yet. GA4 + GSC just started collecting — first organic sessions are the baseline. Demand inferred from sector knowledge + competitor void, not observed usage.

## Status Quo

- Generic analytics queries → PRISM; situation-report queries → ReliefWeb (the source of Sightline's own data).
- Sightline: `/crisis/<slug>` pages carry badges, top-5 report links, HDX figures, GDACS alerts — all real data but zero synthesis. Headline is "545 reports · Protection and Human Rights" (`country_summary.py:177`). Nothing Google can rank against ACAPS's brief analysis or The New Humanitarian's journalism.
- Internal wiring gap (subagent finding): `generate_crisis_summary()` in `weekly_bulletin.py:369` ALREADY does per-country LLM synthesis returning structured JSON (`headline`, `summary`, `severity`) — but runs weekly, capped at `max_tokens=300`, with its own prompt, and its output never reaches the crisis page SSR. The daily country-summary cron (`country_summary.py`) deliberately runs NO LLM (`_build_data_narrative()`, line 158).
- **Pipeline separation fact (from adversarial review):** `output/country_summaries/{Country}.json` is rebuilt DAILY at 06:15 UTC by the country-summaries cron (`deploy/setup-crons-docker.sh:53`) with a fixed schema and a full file overwrite (`country_summary.py:416`) — unknown fields are destroyed. The SSR read path is also a field whitelist: `_crisis_page()` renders from `_crisis_country_data()` → `api_map_countries()` (`public_bp.py:345-377`), which passes only known fields. Therefore enrichment content must live in its OWN artifact (digest JSON files) and be read directly — never injected into summary files.

## Target User & Narrowest Wedge

- The human: M&E / PMER officer + crisis-time news consumer (journalist, donor desk, public) — same two-stage reader→producer coin as the Aug 30 design.
- Narrowest wedge: the daily "Latest developments" section on `/crisis/<slug>` pages — real synthesis text Google can rank, rendered from real data, shipped in days. The digest and deep-dive tiers extend from strength.

## Constraints

- Solo developer; Python Flask monolith; SQLite + ChromaDB; Docker on ARM64 Hetzner (2 vCPU, 4GB).
- **ARM64 ChromaDB constraint (verified, `chroma_adapter.py:536-545`):** whole-collection `collection.query()` and `count()` segfault (untrappable C-level crash) on the production box. Content engine must fetch chunks via SQLite (`get_chunks_by_country_and_themes()`) — never via ChromaDB ad-hoc queries.
- Token budget: founder's original fear was "çok büyük token harcamadan". Vector-store extraction + explicit-model synthesis caps this at ~$0.01/day for the whole engine.
- P2 hard rule (inherited): programmatic content only from REAL data. Never template copy. No report = no digest that day.
- All outputs in English. UI copy: no em dashes; "trusted sources" style general attributions.

## Premises

1. **P1 (agreed):** Content enrichment runs alongside the existing ingest pipeline (daily cron after 06:00 ingest). No new data sources.
2. **P2 (agreed, REVISED after cross-model challenge):** Chunk extraction goes through **SQLite** (`get_chunks_by_country_and_themes()`, `chroma_adapter.py:452` — country+date filtered, already works), not ChromaDB queries. Original premise said "query ChromaDB for top-K chunks" — rejected because `collection.query()` segfaults on ARM64 production. Then the LLM synthesizes (~3-6K tokens/country/day ≈ $0.001).
3. **P3 (agreed):** Replicate the ACAPS model: short + structured. Per country per day: key developments, key concerns, humanitarian impact, information gaps — 150-300 words. (ACAPS users valued "brevity of snapshot texts, brief analysis, key concerns" — independent study, 2014.)
4. **P4 (agreed):** Three-tier output: (A) enrich `/crisis/<slug>` pages with a daily "Latest developments" section, (B) daily digest page for top 10 crisis countries (fresh indexable URL daily), (C) weekly deep-dive analyses for top 3-5 crises (300-500 words each).
5. **P5 (agreed, inherited):** All content from real data only — never template, never filler. No report = no digest that day. "Data pending" beats empty content.
6. **P6 (reworded per review):** This is prompt + schema + cadence work, not pure wiring: JSON-parsing, `chat_simple()` LLM-call plumbing, and Flash-class synthesis all exist (`generate_crisis_summary()` proves the pattern), but the ACAPS-style system prompt, the 5-field output schema, and the daily cadence are new.

## Approaches Considered

### Approach A: Crisis page enrichment only
One script + a new section in `_crisis_page()`. Deepens existing 30-49 pages, zero new surface, lowest P2 risk. Rejected as the whole plan: no new indexable URLs, no daily freshness signal — deepens pages Google hasn't ranked yet.

### Approach B: Three-tier engine — CHOSEN
(A) Daily "Latest developments" on crisis pages, (B) daily digest page (top 10 countries), (C) weekly deep dives (top 3-5 crises, 300-500 words). Effort M (human ~1-2 weeks; agent-assisted ~2-3 days). Risk Low-Med (P2 gate + empty-day handling).

### Approach C: Digest-first flip
Daily flagship briefing URL as the habit surface, enrichment later. Rejected: leaves the original pain (thin crisis pages) unfixed while building a new surface; digest entries would link to pages still too thin to convert.

## Recommended Approach

**B — Three-tier engine**, sequenced exactly as the founder chose in Q4: crisis pages first (fixes the standing pain on already-indexed surface), then digest (daily fresh crawl target), then weekly deep dives (the depth that differentiates from ReliefWeb's feed and rivals ACAPS's brief analysis).

### Architecture

**Storage rule (from adversarial review — critical):** enrichment output lives ONLY in `output/daily_digests/{date}/{Safe_Country}.json`. It never mutates `country_summaries/*.json` (rebuilt daily at 06:15 by another cron with full overwrite + fixed schema) and never relies on field passthrough from `api_map_countries()` (whitelisted). Readers fetch digest files directly by deterministic path (`safe_filename(country)`).

**Eng-review decisions (2026-09-17, D1-D12):** D1 all LLM-derived fields pass `_sanitize_html()` at render + schema-validate (strings only) digest JSON at write. D2 enrichment wrapped `|| true` with status file (`output/daily_digests/status.json`), never fails the scheduler block. D3 indefinite archive accepted (~7MB/year). D4 single loader module `sitrep/daily_digest.py` (`load_digest`/`load_day`) with 5-min in-process cache; script and SSR both import it. D5 date = COVERAGE date (yesterday); `_crisis_page()` walks backward from today up to 3 days to find the newest digest. D6 all 16 test gaps into plan. D7 5-min digest-index cache in `daily_digest.py`. D8 enrichment runs after visual pipeline step and must NOT load embedding models. D9 max_tokens=800 + fence-stripping + HDX in prompt (ChromaAdapter import accepted — `get_chunks_by_country()` is SQLite-only). D10 deep-dive script and `/digest/<date>` sitemap entries DEFERRED to post-baseline; D11 HDX figures in prompt + first-chunk-per-report sampling + pseudo-country filter + tmp+rename atomic writes; D12 stale-digest freshness in `/api/health` + kill criteria (below).

**Data flow (all existing components, new wiring):**

**System prompt (ACAPS style, structured):** factual synthesis from provided chunks only; no speculation; information gaps stated explicitly; attribution to "trusted sources" (general, per UI copy rules); never invent numbers — all figures come from HDX context, not the LLM.

**Cost envelope:** 10 countries/day × (input ~4.5K [20 chunks × ~200 tok + scaffold] + output ~400 tokens) on Gemini 2.5 Flash (explicit `model=` override, list pricing $0.30/M in + $2.50/M out) ≈ **1.35M input + 120K output tokens/month ≈ $0.70-1.50/month** — recomputed after outside-voice correction (input dominates, not output). Consistent with the Success Criteria guardrail. Token fear resolved by architecture + explicit model choice, not by budget increase.

**Publish predicate (P5 gate):** a country gets a daily digest entry iff it had ≥1 report in the last 7 days AND ≥1 ingestible chunk AND its LLM call succeeded. `/digest/<date>` renders only countries that passed; 404 if none.

**Digest linking note:** digest entries link to `/crisis/<slug>` pages that may be below the `_is_crisis_publishable()` gate (noindex). That is acceptable — internal navigation, not sitemap submission — but digest pages link only to crisis slugs that exist; missing slugs render as plain text.

**Scheduler timeline (single source of truth):** enrichment runs INSIDE the `daily_scheduler.sh` lock block, immediately after `daily_ingest.py` succeeds (same container, same loop — no new crontab entry). The country-summaries cron (06:15, crontab via `setup-crons-docker.sh`) is untouched and now file-independent (digest files are separate artifacts), so the two pipelines can run in any order without racing.

### Sequencing (solo dev)

1. **Days 1-2 — Tier A:** `daily_content_enrichment.py` (sampling, explicit model, failure handling) + `_crisis_page()` direct digest-file read + "Latest developments" section + tests (P2 gate, digest-file path resolution, empty-day fallback).
2. **Days 3-4 — Tier B:** `/digest/<date>` + `/digest/<date>/<slug>` + `/digest` archive routes, sitemap integration (digest lastmod + crisis-page digest-date lastmod candidate), tests.
3. **Day 5+ — Tier C:** `generate_deep_dives.py` weekly cron in `setup-crons-docker.sh`, `output/deep_dives/{week}/` artifacts, bulletin `deep_dives` field, tests.
4. **Continuous:** GA4 page-view + GSC weekly snapshot comparison: do enriched crisis pages and digest pages earn impressions/clicks vs the pre-enrichment baseline?

## Kill Criteria (D12 — added from outside-voice challenge)

- **Baseline (now):** record GSC organic impressions/clicks for /crisis/ pages BEFORE enrichment ships — the weekly GSC snapshot (existing cron, Mon 07:30) already captures this.
- **Review point: week 8 after Tier A ships.** Organic impressions on enriched crisis pages trending up (any sustained week-over-week growth) → continue; add the deferred Tier C deep dives.
- **Kill criterion:** impressions flat over 8 weeks → STOP the daily digest cron (keep crisis-page enrichment — it costs nothing to leave live). Rationale: the outside voice's strongest argument — a low-authority domain near-duplicating ReliefWeb content may never rank regardless of content volume; if the data says so, stop feeding it.
- **Cost guardrail unchanged:** < $5/month (expected ~$0.70-1.50 — recomputed with input tokens: 1.35M in + 120K out per month).

## Success Criteria

- **Primary (3 months):** weekly GSC snapshot shows enriched `/crisis/` pages earning impressions and clicks trending up from the current near-zero baseline; ≥1 `/digest/<date>` page indexed per publishing week.
- **Leading:** "Latest developments" section present and populated on all published crisis pages within 1 week of Tier A shipping. **Digest volume (≥5 countries/day on average) is an ENVIRONMENTAL metric — it measures ReliefWeb's daily output, not build quality; build acceptance is that the engine publishes for every country that passes the predicate.**
- **Quality gate:** spot-check 5 digests/week manually — no fabricated figures, no speculation, information gaps stated. Any fabricated number = prompt regression, fix before next cron.
- **Cost guardrail:** monthly OpenRouter spend attributable to the engine stays under $5 (expected ~$0.30-1).
