## Problem Statement

Sightline's Phase 1 SEO surface shipped this week: `/map` SSR page, per-file sitemap lastmod, enriched JSON-LD, GA4 (`G-SJMDY64ZKG`) on every surface, login-overlay removed for anonymous visitors, SITREP/DB/Home freemium flows polished. The site is now crawlable and measurable. But it has near-zero organic traffic: Google has no reason to rank a handful of thin pages, there is no conversion path from reader to user, and measurement stops at raw page views.

Goal (founder's stated answer, 2026-08-30): **both** — organic traffic builds authority/credibility AND a meaningful share of it converts into real users. Not vanity metrics.

## Demand Evidence

- Founder is a sector insider (humanitarian orgs; crisis-time SITREP production is a documented all-nighter problem).
- Competitive landscape (live web, 2026-08-30): PRISM (prismonitor.eu) owns generic "humanitarian dashboard/analytics" queries with 45+ datasets, 27 live feeds, AI analyst, citation-linked answers. Grant-writing SaaS (FundRobin $0-100%, Instrumentl, Grantable, Bloomerang, GrantHub) owns "AI grant writing" — none bind live crisis data.
- Gap that remains unclaimed: **crisis × country × theme long-tail queries** ("sudan sitrep", "türkiye deprem durum raporu") + real-time spike queries at the moment a disaster hits (GDACS alerts live on Sightline).
- Honest gap (unchanged): no external user count yet. Demand inferred from sector knowledge + competitor void, not observed usage. GA4 just started collecting — first organic sessions is a new baseline.

## Status Quo

- Generic analytics queries → PRISM (authority, years of content).
- Situation-report queries → ReliefWeb (the source of Sightline's own data, but with a dated UX and weak crawlable presentation; individual report URLs are deep and noisy).
- Grant proposals → generic AI wrappers with no live data binding.
- Sightline: handful of indexable pages; no programmatic content; no reader→action CTA on public pages; no GSC feedback loop.

## Target User & Narrowest Wedge

- The human: M&E / PMER officer at a humanitarian NGO, plus the crisis-time news consumer (journalist, donor desk, public) who searches during an event.
- Two-stage coin: **reader** (searches "sudan sitrep", lands on a real, current, rich page) → **producer** (in-crisis: "Get this as a sitrep" CTA opens the generation flow — the wedge from the Aug 23 plan).
- Narrowest deposit: the long-tail page IS the product sample; the CTA is the demo door. No account required to read; generation is premium-gated as designed.

- No paid ad budget: organic only.

- Proposal Studio separate repo (embedded via bridge) — changes under `proposal/` follow its repo.
- P2 hard rule: programmatic pages only from REAL data (report counts, live GDACS alert level, HDX figures). Never empty template copy — Google penalty + reputation risk on a humanitarian trust product.

## Premises

1. **P1 (agreed):** Do not fight PRISM on generic analytics keywords. Our arena = crisis × country × theme long-tail + real-time event spikes (live GDACS).
2. **P2 (agreed):** Programmatic pages only from REAL live data (report counts, live GDACS alert level, HDX figures). Empty scaffolding never ships. **Publish predicate:** a country gets a `/crisis/<slug>` page iff `report_count >= 3` OR a live GDACS alert is present; below-threshold countries are excluded from the sitemap and left `noindex` (no thin pages, no crawl bait). Expected initial count: ~30-45 of 143 countries; page set grows as ingest covers more countries. (Single type per page — country; no country×crisis-type matrix in this phase.)
4. **P3 (agreed):** Reader→conversion is staged: information consumer → in-crisis "make this a sitrep" need → demo → org sale. Pages therefore carry crisis-focused CTAs; readers who consume now, produce later. **CTA activation is measured via a dedicated GA4 event (`cta_click` with `cta_name=make_sitrep`) fired on click — measurement ships with the CTA, not retrofitted.**
5. **P4 (agreed):** Measurement = GA4 + Google Search Console linked (which pages indexed, which queries drive traffic, GSC API for automated weekly report). Targets: monthly organic session growth + indexed-page growth.
6. **P5 (non-goal, added):** **No i18n in this phase.** Turkish-speaking users searching "türkiye deprem durum raporu" land on the English page; localization is out of scope until traffic proves a non-English audience exists.

## Approaches Considered

### Approach A: Foundation Close-out (minimal — 2-3 days)
- Search Console: submit `/sitemap.xml`, verify property, GA4-GSC link, manual index requests for `/map`, `/bulletins`, top SSR pages.
- Add crisis-focused CTAs ("Get this as a sitrep", "Run this as an analysis") + a one-line metadata enhancement (page description already present) to existing SSR templates.
- Effort: S. Risk: Low. Reuses: existing `_render_list`/`_render_detail` plumbing.

### Approach B: Programmatic Crisis Pages Engine (the growth motor — 1-2 weeks)
- Generate `/crisis/<country>` pages for all p...ublishing countries from real data **materialized at ingest time**, not fetched per-request:
  - **Materialization (NOT per-request SSR):** at each ingest cycle, a writer materializes a rendered content fragment per qualifying country into SQLite (report_count, top themes, GDACS alert snapshot, HDX figures + rendered HTML). The route SSRs from local SQLite only → fast TTFB, no external rate-limit risk when Googlebot bursts, no collapse on the 2 vCPU/4GB box during a disaster spike (exactly when these pages matter).
  - **lastmod** = the materialized row's mtime; sitemap reads it (already per-file lastmod, now per-row).
  - `noindex` on below-threshold countries (publish predicate in P2); expected ~30-45 pages initially.
- **Page content model (per `/crisis/<slug>`):** H1 = `{Country} — live crisis overview`; sections = (1) Current alert (GDACS level + recent alerts, labeled "as of <timestamp>"), (2) Reports (count + top-5 recent titles w/ links, theme chips), (3) Key figures (HDX: people affected/displaced where available), (4) Updates (linked bulletins/SITREPs for the country), (5) CTA block ("Get this as a sitrep"). Per-source failure → that section renders "Data pending" state, page still ships with what exists (never blocks on an external source).
- **JSON-LD:** Dataset/WebPage schema on aggregate pages — NOT NewsArticle (autogenerated aggregate pages with NewsArticle schema are a well-known spam-signal pattern; NewsArticle reserved for genuinely alert-triggered "breaking" pages only). Validate with Rich Results Test in QA.
- Sitemap extended; `lastmod` per row; linked via `/crisis/<slug>` namespace (no conflict with existing `/country/<slug>` — separate route family).
- Effort: M. Risk: Low-Med (anti-spam risk mitigated by P2 data rule + noindex gate). Reuses: `api_map_countries`, `_map_context`, sitemap builder, existing templates.

### Approach C: Ideal Architecture (2-4 weeks)
- B + GDACS-triggered "breaking" pages (a new alert above threshold auto-creates `/crisis/<country>` content immediately, not waiting for next ingest) + GSC API weekly dashboard (queries, indexed pages, clicks → dedicated table in the app SQLite DB (NOT chats.db — that store is conversation-scoped and rotated; growth data must survive), surfaced in Admin analytics).
- GDACS-trigger details (when C-lite ships): poll every 15 min; trigger = new orange/red alert; staleness labeling ("as of …", never a 3-day-old alert shown as breaking); `lastmod` churn cap (max 2 refreshes/day per country) to avoid crawl-bait behavior.
- Effort: L. Risk: Med. Reuses: B engine, helpers, admin analytics.

## Success Criteria

- **Primary:** `site:sightlinehumanitarian.com` shows /crisis/ pages indexed within 3 months of sitemap submission; weekly GSC snapshot shows organic clicks > 0 trending up; ≥2 "Get this as a sitrep" CTA activations (`cta_click` GA4 event) from **anonymous visitors from any channel** within 3 months of A shipping (measurement baseline starts at A; CTA clicks fire a dedicated GA4 event so the count is real, not guessed).
